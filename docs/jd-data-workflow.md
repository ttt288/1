# 京东榜单数据整理方案

## 2026-09-08 复核与当前限制

已实现公开页面 HTTP 采集和 Beautiful Soup 解析。页面打开、开始分析时检查 6 小时缓存；用户也可以手动刷新（30 秒防连点）。没有后台定时任务，关闭页面后不会自动抓取。采集不调用 LLM。

旧榜单与本地商品的配方、规格和评论数未完成逐 SKU 核验，已停止挂接未核实的排名和加分。商品价格及成分为待核验参考数据。last_updated 是本地资料日期；ranking_observed_at 单独记录榜单采集日期，两者均不代表平台发布时间。

已经保存原始 HTML、内容哈希、独立快照及刷新状态。刷新失败保留旧快照，自动检查失败后等待 5 分钟再试。内容未变时更新最近检查和成功采集时间，保留内容变化时间；平台发布时间缺失则保持空值。

本地商品只有 jd_sku 唯一且规范化重量与榜单一致才参与匹配，不按相似品牌匹配。包装乘数或规格不明确时不匹配。匹配成功也不会覆盖价格和配方；这些字段仍待独立核验。榜单未匹配条目在页面单独展示，不填造缺失价格来凑推荐候选。

当前进程内锁避免并发重复采集，文件通过原子替换写入，适用于本机单进程运行。多 worker 部署前需要共享锁。快照或本地商品文件改变会使商品搜索缓存失效，已有会话保留原候选以维持回答一致性。

## 操作与接口

- 页面中展开“查看榜单商品”，可见真实排名、SKU、标题、图片、评论数及匹配原因。
- “刷新榜单”主动检查数据；“检查成功，榜单内容未变化”表示请求执行成功。
- `GET /api/market/jd`：读取状态及匹配情况，不联网。
- `POST /api/market/jd/refresh`：按缓存有效期检查。
- `POST /api/market/jd/refresh?force=true`：手动刷新。
- 刷新后重新“开始分析”才使用新候选，不中途更换已回答问题对应的商品。

## 目标

项目不追求实时全网最低价，而是把京东公开榜单整理成可追溯的候选召回信号。推荐链路使用这些信号回答三个问题：

- 当前品类有哪些真实热卖候选。
- 候选之间有哪些差异值得追问用户。
- 个性化排序为什么不同于只看销量或只看低价。

## 数据分层

1. 京东榜单信号
   - 来源：公开排行榜、金榜、类目榜。
   - 可用字段：榜单名、URL、观察日期、排名、标题、品牌、评论量级、榜单标签。
   - 用途：提升候选商品热度可信度，帮助 Product Discovery Agent 召回。

2. 人工校验商品库
   - 来源：商品详情页、品牌页、包装/配料表、官方旗舰店信息。
   - 可用字段：价格、规格、单价、适用阶段、主要成分、功能卖点、风险标签、适合/不适合人群。
   - 用途：用于排序、风险规则、动态问题生成。

3. 本地知识库
   - 来源：宠物食品规则、成分解释、保健品风险边界。
   - 用途：决策型 RAG 的推荐依据，不直接替代商品数据。
